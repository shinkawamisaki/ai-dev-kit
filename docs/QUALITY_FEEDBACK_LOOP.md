# 品質管理とフィードバックループ

この体制は「AI 生成コードの品質を、複数レイヤーで段階的に保証する」ことを目的とする。
AI による主観的検証（設計思想に基づく判断）と、ツールによる客観的検証（静的解析）を
適材適所で組み合わせる。

## レイヤー構造

```
Layer 0  コーディング        writer（AI エージェント）+ AGENTS.md
Layer 1  pre-commit（任意）   secret スキャン・lint・フォーマッタ（ローカル即時・skip 可）
Layer 2  PR 時の自動検査      ── 強制ゲート ──
           A: 静的解析（外部標準ツール / 言語・スタックに応じて差し替え）
           D: AI レビュアー（AGENTS.md + logs/active_rules.md / 設計思想の判断）
           + D の回帰テスト（eval・検閲基準を変える PR のみ）
Layer 3  人間レビュー         最終ゲート（CODEOWNERS 等）
```

## Layer 2 の責任分界（このキットの核心）

検証を「根拠」で役割分担する。**外部標準に委譲できるものはツールへ、設計思想が要るものは
AI へ**。これを混ぜない。

| 種別 | 担当 | 根拠 | フィードバックの向き |
|---|---|---|---|
| A: 静的解析（secret/lint/SAST 等） | 外部ツール | 公式ルールセット・標準 | 設定で緩める方向 |
| D: AI レビュアー | このキット | `AGENTS.md`（憲法）+ `logs/active_rules.md`（判例） | **判例蓄積で精度を上げる方向** |

> A（外部ツール）は「ツールのカバレッジ限界」で取りこぼす。D（AI）は「判例の不足／
> プロンプトの曖昧さ」で取りこぼす。**D だけが、判例を足すほど賢くなる**。この非対称が
> 体制の価値の中心。A は言語・クラウドに応じて自由に差し替えてよい（プラガブルなスロット）。

## D（AI レビュアー）のフィードバックループ

```
AI が FAIL を出す / 人間が判定ミスに気づく
      │
      ▼
人間が判断（エスカレーション）
      │         │
      ▼         ▼
judgments.md   active_rules.md      ＋ evals/cases/ にケース追加
（証跡・追記）  （判例・upsert）        （回帰テストに固定化）
      │
      ▼
次の PR で AI レビュアーが自動で読み込む → 判定精度が上がる／再発を機械検知
```

人間の介入は「最終判断の明文化」だけで完結する。判例が貯まるほど自律的に精度が上がる。

## 構造的担保（緩めると強制力が失われる）

このキットがゲートとして成立するのは、以下を**構造で**守っているから。詳細と「変えてよい層/
変えてはいけない層」は [../README.md](../README.md) を参照。

- **fail-closed**: 判定不能（インジェクション成功・形式逸脱・API 障害）は合格にしない。
- **審査基準は PR の base コミットから読む**: ルールを骨抜きにする PR を骨抜き前の
  ルールで審査する（自己参照の遮断）。
- **eval と本番が同一プロンプトを読む**: `prompts/reviewer_prompt.txt` を両者が参照し、
  「eval は通るが本番は別プロンプト」という形骸化を防ぐ。
- **writer と reviewer は別系統**: コードを書く AI とレビューする AI を同一にしない。
- **判例の二層構造**: `judgments.md`（append-only の証跡）と `active_rules.md`
  （upsert の現行判例）を分離する。

## 自動化の境界（設計哲学）

「例外か違反か」の最終判断は設計思想に依存し、完全自動化は困難。よってこの体制の自動化の
ゴールは **「人間の判断を要求するところまで情報を整理して運ぶこと」** に置く。バグが出たら
「どのレイヤーが検出すべきだったか」を特定し、該当レイヤーの仕組み（A の設定 / D の判例）を
改善する。これが長期的な品質安定化の鍵になる。
